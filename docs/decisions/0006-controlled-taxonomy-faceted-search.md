# 0006 管理語彙と複数選択ファセット検索を採用する

- 日付: 2026-08-30
- 状態: 採用

## 決定

カテゴリを人間の使用場面を表す14種類の管理語彙へ統合し、Resourceは1〜3カテゴリへ所属できるようにする。タグは具体的な技術特性を表す管理語彙とし、AIによる自由作成を禁止する。種類、カテゴリ、タグは複数選択でき、同じFacet内をOR、異なるFacet間をANDで検索する。

公開検索ではMCP、Skill、BlogをContent Typeとし、ZennとQiitaはBlogのSourceとして扱う。既存の`zenn_article`と`qiita_article`は初回リリースでは維持し、検索境界でBlogへまとめる。

## 理由

公開400件に対してカテゴリ233種類、タグ1,233種類が作られ、カテゴリ179種類、タグ1,021種類が1件にしか使われていなかった。自由分類を維持したままUIだけを複数選択化しても、利用者が期待する分類名と結果の一致を改善できない。

人間が語彙と粒度を定義し、AIはその中から選ぶ方式なら、分類の一貫性、検索の説明可能性、管理者による修正可能性を維持できる。

## 却下した選択肢

- 既存カテゴリ・タグをそのままチェックボックス化する案: 無意味な選択肢と類義語が残る。
- AIが必要に応じてカテゴリ・タグを自動作成する案: 継続取込で語彙が再び増殖する。
- Content TypeをMCP、Skill、Zenn、Qiitaの4種類として公開し続ける案: 記事という種類と公開元という概念が混在する。

## 影響

- ResourceとCategoryを多対多へ変更する。
- 旧`resource_tags`をロールバック用に温存し、新分類のTag関係を加算的な別テーブルへ保存する。
- 固定14カテゴリと初期TagはYAMLから同期し、監査済みの管理者追加TagはDBの実行時許可リストと初期カタログArtifactへ含める。
- AI分類候補、管理画面、検索、推薦、初期カタログの変更が必要になる。
- 本番移行は加算的に行い、旧`category_id`と旧分類を初回リリースでは削除しない。
- 任意のFacet組み合わせによる検索ページは`noindex, follow`にし、SEO URLの組み合わせ爆発を防ぐ。
